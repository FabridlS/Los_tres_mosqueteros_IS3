# Título: ADR-006 Validación Robusta y Control de Errores ante APIs Externas y Carga Masiva (Módulo de Inscripciones)

**Estado:** Aceptado

**Fecha:** 2026-06-17

**Decisores:** DA ROSA Jesica M., de LOS SANTOS Fabrizzio R., GRABOVIESKI Matias A.

**Relacionado:** spec-inscripcion.md

**Contexto**
- **Qué problema se está resolviendo:** El endpoint de inscripción masiva por lotes de correos electrónicos (`POST /events/:id/enroll/bulk`) procesa datos múltiples en una sola petición. Existe el riesgo de inyectar caracteres maliciosos que afecten al backend o que la base de datos falle a mitad del proceso, dejando registros corruptos o incompletos. También se deben mitigar ataques DoS por cargas excesivamente grandes.
- **Qué restricciones aplican (negocio, técnica, legal):** Cumplimiento estricto de las directrices OWASP detalladas en los criterios de aceptación del spec de inscripciones. Se debe evitar la enumeración de usuarios en los errores devueltos a actores externos.
- **Qué datos de proyecto sustentan la decisión:** La HU-INS-04 del módulo de inscripciones exige explícitamente la adopción de controles de Rate Limiting, límites de tamaño en el payload y validaciones individuales libres de inyecciones de SQL o ataques ReDoS.

**Decisión**
- **Qué se decide exactamente:** Implementar un middleware de validación estructurada con la librería **Zod** para procesar de forma atómica cada email del arreglo recibido, complementado con la ejecución del lote dentro de una transacción interactiva de Prisma (`prisma.$transaction`).
- **Alcance (qué cubre y qué no cubre):** Cubre la validación de estructura, el control de errores semánticos y la integridad transaccional de las inscripciones masivas asistidas por el Staff. No cubre la lógica de confirmación por pasarelas de pago ni validaciones en otros formularios del sistema.

**Alternativas consideradas**
- **Opción A (Validación en bucle iterativo sin transacciones):**
  - *Pros:* Fácil codificación mediante un ciclo `for` o `forEach` nativo de JavaScript.
  - *Contras:* Si el email número 50 de una lista falla por un error inesperado, las 49 inscripciones anteriores se guardan y las siguientes se descartan, provocando inconsistencia total de datos y estados indeterminados.
- **Opción B (Delegar la validación y captura de errores únicamente al motor PostgreSQL):**
  - *Pros:* Reduce código en la capa del backend.
  - *Contras:* Revela detalles internos del esquema de base de datos a través de los mensajes de error HTTP (infringiendo OWASP) y expone al servidor a bloqueos de recursos por denegación de servicio si el input es masivo.

**Consecuencias**
- **Beneficios esperados:** Garantía de atomicidad: el lote de inscripciones se procesa completo o no se guarda nada (todo o nada). Protección robusta de la API contra payloads maliciosos y control estricto de la información devuelta (ocultando existencia previa de correos en el sistema).
- **Costos o riesgos que se aceptan:** Mayor uso de tiempo de CPU y bloqueos momentáneos de registros en la tabla `enrollments` durante la ejecución de transacciones extensas.
- **Impacto en operación y equipo:** Los desarrolladores deben estructurar esquemas de validación Zod muy precisos y específicos para cada carga masiva de datos.

**Plan de implementación**
- **Pasos mínimos para ejecutarla:** Definir el esquema `bulkEnrollmentSchema` en Zod. Configurar un tamaño límite de carga en el body parser de Express (`express.json({ limit: '1mb' })`). Envolver la iteración de inserciones en un bloque `prisma.$transaction` y mapear los errores para retornar códigos limpios y unificados.

**Dependencias**
- Librería `zod` y Prisma ORM 5+.

**Métrica de éxito**
- El endpoint rechaza payloads superiores a los límites establecidos de forma inmediata y mantiene la base de datos libre de registros huérfanos o parciales ante caídas simuladas en los tests de integración.

**Triggers de revisión**
- **Qué condiciones obligan a reabrir esta ADR:** Necesidad de delegar el procesamiento a servicios Workers en segundo plano (Background Jobs) si las listas de emails provistas por el personal superan habitualmente los 1,000 registros por tanda.
