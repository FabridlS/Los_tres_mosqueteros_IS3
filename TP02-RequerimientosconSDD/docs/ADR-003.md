# Título: ADR-003 Almacenamiento de Estructuras Dinámicas de Encuestas mediante el tipo de datos JSONB en PostgreSQL

**Estado:** Aceptado

**Fecha:** 2026-06-17

**Decisores:** DA ROSA Jesica M., de LOS SANTOS Fabrizzio R., GRABOVIESKI Matias A.

**Relacionado:** spec-encuestas.md

**Contexto**

- Qué problema se está resolviendo: El módulo de encuestas requiere soportar diferentes tipos de cuestionarios con preguntas y opciones completamente dinámicas (múltiple opción, texto libre, escalas numéricas de feedback). Diseñar esto bajo un modelo puramente relacional rígido generaría una cantidad excesiva de tablas intermedias e implicaría múltiples operaciones JOIN complejas que degradarían el rendimiento a medida que crezca el volumen de respuestas recolectadas.
- Qué restricciones aplican (negocio, técnica, legal): Se debe mantener el motor de base de datos PostgreSQL y el ORM Prisma ya adoptados en la arquitectura base del proyecto. No se contempla la migración de la persistencia global a un modelo NoSQL puro por cuestiones de consistencia e integridad referencial con el resto de los módulos tradicionales del sistema (usuarios, inscripciones y eventos).
- Qué datos de proyecto sustentan la decisión: Las especificaciones funcionales dentro de `spec-encuestas.md` detallan que cada organizador puede personalizar su formulario de feedback de manera independiente para cada evento, variando constantemente la cantidad de preguntas y el tipo de campos obligatorios de consulta.

**Decisión**

- Qué se decide exactamente: Utilizar el tipo de datos nativo `JSONB` de PostgreSQL mapeado a través de Prisma para almacenar de forma semiestructurada la definición de las preguntas y la matriz de las respuestas correspondientes dentro de la tabla de encuestas.
- Alcance (qué cubre y qué no cubre): Cubre el diseño, almacenamiento y recuperación de los formularios dinámicos y las respuestas recolectadas en el módulo de encuestas. No cubre las relaciones de clave foránea principales (como la asociación directa del registro con el ID del usuario o el ID del evento), las cuales seguirán estructuradas como columnas relacionales estándar de tipo entero o UUID.

**Alternativas consideradas**

- Opción A (Modelo Relacional EAV - Entity-Attribute-Value):
- Pros: Mantiene un esquema puramente relacional clásico sin requerir tipos de datos avanzados o específicos del motor.
- Contras: Requiere consultas SQL sumamente extensas y costosas con numerosos JOINs para reconstruir una sola encuesta, afectando de manera crítica los tiempos de respuesta del servidor durante picos de alta concurrencia.


- Opción B (Base de Datos NoSQL Híbrida como MongoDB):
- Pros: Manejo de documentos altamente flexible por naturaleza, ideal para la persistencia de formularios variables.
- Contras: Introduce una gran complejidad técnica y de mantenimiento en la infraestructura del servidor al tener que administrar y sincronizar dos motores de base de datos distintos de manera simultánea.



**Consecuencias**

- Beneficios esperados: Flexibilidad absoluta para modificar, quitar o añadir tipos de preguntas sin necesidad de alterar el esquema físico de la base de datos ni ejecutar migraciones de tabla complejas, permitiendo lecturas eficientes en un solo paso y un almacenamiento compacto.
- Costos o riesgos que se aceptan: Se pierde la validación estricta de tipos y restricciones a nivel de esquema nativo de la base de datos para los atributos internos del JSON, trasladando la total responsabilidad de la validación estructural al código del backend en TypeScript.
- Impacto en operación y equipo: El equipo de desarrollo deberá tipar rigurosamente las interfaces de TypeScript correspondientes para mapear los objetos JSON y aprender a utilizar las funciones de filtrado anidado de Prisma para la generación de reportes estadísticos.

**Plan de implementación**

- Pasos mínimos para ejecutarla: Modificar el archivo `schema.prisma` definiendo los campos de estructura y respuestas como tipo `Json`, ejecutar el comando de migración correspondiente, y desarrollar esquemas de validación robustos utilizando librerías como Zod en el backend para asegurar la integridad de los datos antes de persistirlos.

**Dependencias**

- Soporte nativo del tipo de datos JSONB en la instancia activa de PostgreSQL y compatibilidad de tipos JSON habilitada en Prisma ORM.

**Métrica de éxito**

- Capacidad de almacenar y recuperar con éxito formularios con esquemas de preguntas completamente heterogéneos dentro de una misma tabla, manteniendo tiempos de respuesta de consulta de lectura inferiores a los 100ms.

**Triggers de revisión**

- Qué condiciones obligan a reabrir esta ADR: La necesidad imperiosa de realizar análisis estadísticos relacionales cruzados de extrema complejidad que vuelvan ineficiente el parseo y la indexación del formato JSONB desde queries nativas.
