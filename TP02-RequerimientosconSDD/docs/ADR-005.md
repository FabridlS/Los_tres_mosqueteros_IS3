# Título: ADR-005 Esquema de Autenticación y Gestión de Cuentas mediante JWT (JSON Web Tokens)

**Estado:** Aceptado

**Fecha:** 2026-06-17

**Decisores:** DA ROSA Jesica M., de LOS SANTOS Fabrizzio R., GRABOVIESKI Matias A.

**Relacionado:** project.md

**Contexto**
- **Qué problema se está resolviendo:** Se necesita definir el mecanismo de autenticación y autorización para los usuarios de la plataforma (organizadores, participantes, staff y administradores). El sistema debe ser seguro, eficiente y capaz de proteger las rutas y recursos de la API REST de forma descentralizada.
- **Qué restricciones aplican (negocio, técnica, legal):** La aplicación web es un desarrollo que divide Frontend (React) y Backend (Node.js/Express). El protocolo de comunicación debe ser sin estado (stateless) para no sobrecargar la memoria del servidor con sesiones activas y garantizar transferencias rápidas.
- **Qué datos de proyecto sustentan la decisión:** El archivo `project.md` estipula el uso previo de las librerías `jsonwebtoken` para tokens y `bcrypt` para el hash de contraseñas en el backend.

**Decisión**
- **Qué se decide exactamente:** Implementar un esquema de autenticación basado en **JWT** utilizando una estrategia de doble token: un *Access Token* de corta duración (15 minutos) transmitido en las cabeceras HTTP (`Authorization: Bearer`), y un *Refresh Token* de larga duración (7 días) almacenado en una cookie segura con la propiedad `HttpOnly`.
- **Alcance (qué cubre y qué no cubre):** Cubre el control de acceso a todos los endpoints protegidos de los specs del sistema (inscripciones, informes, creación de eventos). No cubre la federación de identidades externas (como login con Google o GitHub) en esta fase del desarrollo.

**Alternativas consideradas**
- **Opción A (Sesiones tradicionales basadas en Cookies + Redis):**
  - *Pros:* Permite la revocación inmediata de sesiones directamente desde el servidor.
  - *Contras:* Introduce estado (stateful) en la API y obliga a mantener una infraestructura de base de datos en memoria (como Redis) dedicada exclusivamente a los IDs de sesión, complejizando el despliegue inicial.
- **Opción B (JWT simple solo en LocalStorage):**
  - *Pros:* Muy fácil de implementar y configurar en el cliente.
  - *Contras:* Altamente vulnerable a ataques Cross-Site Scripting (XSS). Si un script malicioso se ejecuta en el navegador, podría robar el token definitivo del usuario.

**Consecuencias**
- **Beneficios esperados:* La API REST se mantiene completamente libre de estado (stateless), lo que facilita su escalabilidad. Mayor seguridad frente a ataques XSS al resguardar el token de refresco en cookies `HttpOnly` inaccesibles para JavaScript.
- **Costos o riesgos que se aceptan:** Dificultad para invalidar de forma inmediata un *Access Token* antes de que expire (los 15 minutos), riesgo que se mitiga reduciendo al mínimo el tiempo de vida del mismo.
- **Impacto en operación y equipo:** El equipo de frontend debe configurar interceptores (ej. con Axios) para capturar errores 401 y gestionar de forma transparente la renovación de tokens mediante el endpoint `/auth/refresh`.

**Plan de implementación**
- **Pasos mínimos para ejecutarla:** Configurar las variables `JWT_ACCESS_SECRET` y `JWT_REFRESH_SECRET` en el archivo `.env`. Desarrollar el middleware de autenticación en Express para verificar la firma de los tokens y codificar el hash de contraseñas con `bcrypt` en las rutas de registro.

**Dependencias**
- Librerías `jsonwebtoken` y `bcrypt` instaladas en el backend.

**Métrica de éxito**
- Bloqueo inmediato de solicitudes no autenticadas con código de estado HTTP 401 y resolución exitosa de rutas protegidas en menos de 50ms para usuarios con tokens válidos.

**Triggers de revisión**
- **Qué condiciones obligan a reabrir esta ADR:** Descubrimiento de vulnerabilidades críticas en la librería `jsonwebtoken` o cambios de políticas en los navegadores que impidan por completo el uso de cookies en entornos cross-origin de desarrollo.
