# Título: ADR-002 Inclusión de Caché Distribuida (Redis) para el módulo de Eventos

**Estado:** Propuesto

**Fecha:** 2026-06-16

**Decisores:** DA ROSA Jesica M., de LOS SANTOS Fabrizzio R., GRABOVIESKI Matias A.

**Relacionado:** spec-eventos.md, issue de rendimiento

**Contexto**

- Qué problema se está resolviendo: Se anticipa una latencia alta en la consulta principal de eventos disponibles. Se requiere escalar este módulo específico para controlar el acceso concurrente sin saturar el sistema.


- Qué restricciones aplican (negocio, técnica, legal): El catálogo de eventos es de acceso público y masivo, por lo que debe responder rápidamente. Se debe evitar la sobrecarga directa de la base de datos transaccional.
- Qué datos de proyecto sustentan la decisión: El documento spec-eventos.md indica que habrá múltiples consultas de lectura diarias. Consultar permanentemente el motor relacional para datos que cambian con poca frecuencia es ineficiente.



**Decisión**

- Qué se decide exactamente: Implementar Redis como sistema de caché distribuida en memoria para almacenar temporalmente el listado de eventos disponibles.
- Alcance (qué cubre y qué no cubre): Cubre únicamente las peticiones de lectura (GET) del módulo de eventos definido en spec-eventos.md. No cubre la inserción, actualización, operaciones de spec-encuestas.md o del sistema de login y acreditación.



**Alternativas consideradas**

- Opción A (Caché distribuida con Redis):
- Pros: Alto rendimiento, reduce drásticamente las consultas a la base de datos principal, escala de forma independiente y permite compartir la caché entre múltiples instancias del backend.
- Contras: Agrega un nuevo componente a la arquitectura y complejidad técnica en el manejo de invalidación.


- Opción B (Caché en memoria local - MemoryCache):
- Pros: Fácil de implementar directamente en el código sin requerir servicios adicionales.
- Contras: Si la aplicación escala a varios servidores, cada uno tendrá una caché distinta, generando posible inconsistencia de datos para los usuarios.


- Opción C (Optimización directa en la Base de Datos - Índices):
- Pros: No requiere tecnologías adicionales.
- Contras: Aunque mejora el tiempo de consulta, no protege a la base de datos contra picos masivos de tráfico por usuarios recurrentes.



**Consecuencias**

- Beneficios esperados: Tiempos de respuesta inferiores a 50ms para listar eventos, liberación de carga en la base de datos principal.
- Costos o riesgos que se aceptan: Riesgo de mostrar datos temporalmente desactualizados si la sincronización falla (stale data). Aumento leve en el consumo de memoria del servidor.
- Impacto en operación y equipo: El equipo debe adaptar el patrón de acceso a datos de los eventos: primero consultar Redis y, si no hay datos, consultar la base de datos principal y poblar la caché.

**Plan de implementación**

- Pasos mínimos para ejecutarla: Desplegar una instancia/contenedor local de Redis, instalar la librería cliente en el proyecto, y modificar el controlador de eventos para incorporar la lógica de caché con un tiempo de expiración (TTL) sugerido de 5 a 10 minutos.

**Dependencias**

- Servidor Redis operativo y librería de conexión instalada en el proyecto.

**Métrica de éxito**

- Reducción de la latencia en las consultas públicas de eventos en al menos un 70% bajo pruebas de carga.

**Triggers de revisión**

- Qué condiciones obligan a reabrir esta ADR: Quejas recurrentes de usuarios viendo eventos cancelados debido a una mala política de invalidación de caché, o la necesidad de datos en estricto tiempo real (por ejemplo, para venta simultánea de entradas).
