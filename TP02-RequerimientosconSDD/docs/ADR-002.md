# Título: ADR-002 Separación de la Generación de Certificados en Background Jobs (Cola de Tareas)

**Estado:** Propuesto

**Fecha:** 2026-06-16

**Decisores:** DA ROSA Jesica M., de LOS SANTOS Fabrizzio R., GRABOVIESKI Matias A.

**Relacionado:** spec-acreditacion.md (RF-CERT-03.5: "La generación masiva es asíncrona")


**Contexto**
- Qué problema se está resolviendo: Latencia alta. La petición `POST /certificates/generate` para crear masivamente PDFs de certificados bloquea el único hilo (Event Loop) de Node.js, dejando al backend inoperativo para procesar otras requests (como inscripciones o logins) hasta que finalice.
- Qué restricciones aplican (negocio, técnica, legal): La API debe responder rápidamente. Se requiere devolver un estado `202 Accepted` con un `jobId` al cliente.
- Qué datos de proyecto sustentan la decisión: En eventos grandes, la generación simultánea de cientos de PDFs usando `pdfkit` demanda tiempo intensivo de CPU.

**Decisión**
Qué se decide exactamente: Incluir Redis y una librería de gestión de colas (como BullMQ) para separar la carga de trabajo en un módulo independiente (Worker) que procese los certificados asincrónicamente.
- Alcance (qué cubre y qué no cubre): Cubre exclusivamente la generación masiva de reportes y PDFs.

**Alternativas consideradas**
- Opción A (Procesamiento asíncrono básico con setTimeout/setImmediate): 

    Pros: Sin dependencias nuevas. 
    
    Contras: Si el servidor crashea, los trabajos en memoria se pierden; no se puede escalar en múltiples servidores.
- Opción B (Cloud Functions / AWS Lambda): 

    Pros: Escala infinitamente y no consume recursos del servidor principal. 
    
    Contras: Aumenta la complejidad del despliegue y podría generar costos externos si se supera el nivel gratuito.

**Consecuencias**
- Beneficios esperados: La API principal mantendrá latencia baja incluso durante la generación masiva de PDFs. Tolerancia a fallos (BullMQ reintenta trabajos fallidos).
- Costos o riesgos que se aceptan: Se agrega una nueva pieza a la infraestructura (servidor Redis) que hay que monitorear y mantener.
- Impacto en operación y equipo: Hay que instalar Redis localmente o mediante Docker para el desarrollo.

**Plan de implementación**
- Pasos mínimos para ejecutarla: Instalar `bullmq` y `ioredis`. Levantar un contenedor de Redis. Configurar un Queue en la ruta `POST /certificates/generate` que solo encole los datos y responda un HTTP 202. Crear un archivo `worker.ts` que escuche la cola y genere el PDF.

**Dependencias**
- Instancia de Redis accesible desde el backend.

**Métrica de éxito**
- El endpoint `POST /certificates/generate` debe tener un tiempo de respuesta menor a 300ms, sin importar la cantidad de participantes.

**Triggers de revisión**
- Qué condiciones obligan a reabrir esta ADR: Si Redis consume demasiada memoria RAM, o si la librería de colas queda deprecada.
- Fecha sugerida de revisión: 2026-12-01.
